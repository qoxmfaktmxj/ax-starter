# 기능 스펙 설계

이 스킬은 한 기능의 설계와 계획을 다룬다. 첫 실행에서 코드를 구현하거나 배포하지 않는다.

1. 저장소의 `AGENTS.md`, `PRODUCT.md`, `README.md`, `docs/PROGRESS.md`, `docs/MVP_PLAN.md`, `docs/DESIGN_BRIEF.md`, `docs/SOURCE_RECORD.md`와 대상 기능의 기존 설계, 코드, 테스트를 읽는다. `git status --short --branch`와 관련 브랜치의 차이를 확인하고 다른 작업의 미커밋 변경을 보존한다. 오래된 MVP 계획을 현재 구현 상태로 간주하지 않는다.
2. 사용자가 지정한 기능 하나를 대상으로 기존 결정, 현재 구현, 남은 요구사항, 출처, 불확실성을 구분한다. 대상이 없으면 `PRODUCT.md`의 다음 우선순위를 후보로 제시하고 그 선택이 결과를 크게 바꾸면 질문한다. 같은 요구사항을 다른 전역 문서에 복제하지 않는다.
3. `docs/superpowers/specs/`의 기존 형식에 맞춰 기능 스펙을 작성하거나 갱신한다. 문제와 사용자, 포함과 제외 범위, 입력과 출력, 상태와 오류, 권한과 데이터 경계, 제약, 엣지 케이스, AC별 재현 절차와 검증 방법을 명시한다. 화면 기능이면 로딩, 빈 결과, 실패, 접근성, 모바일과 모션 감소 조건을 검토한다. 미확정 사항은 결정으로 꾸미지 않는다.
4. 기능을 구현 가능한 작은 단계로 나누고 각 단계의 대상 파일, 대응 AC, 테스트, 완료 조건을 `docs/superpowers/plans/`의 계획에 기록한다. 선택지가 오래 유지될 아키텍처 결정이면 대안과 장단점을 스펙의 결정 항목에 기록하고, 여러 기능에 영향을 주는 경우에만 별도 ADR을 제안한다.
5. 스펙과 계획의 링크, 근거, 남은 결정, 첫 구현 단위를 보고한다. 영향이 큰 미결정 사항만 최대 세 가지 질문한다. 이미 승인된 결정은 반복 확인하지 않는다. 실행하지 않은 테스트를 통과로 표시하지 않는다. 구현 요청을 별도로 받으면 승인된 AC에 맞춰 테스트와 코드를 진행하고 실제 결과를 `docs/PROGRESS.md`에 기록한다.

`AGENTS.md`를 저장소의 공통 작업 규칙으로 사용한다. 별도 `CLAUDE.md`나 중복 PRD/Architecture 문서를 만들지 않는다. 사용자의 최신 지시와 실제 코드가 문서와 다르면 차이를 드러낸다.
