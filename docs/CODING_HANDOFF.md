# 다음 코딩 모델 인계서

목적: 계획을 재설계하지 않고 로컬 MVP를 구현한다. 이 문서는 계획 작성 시점에 만들었다. 이후 구현과 검사 결과는 [PROGRESS.md](PROGRESS.md)를 먼저 확인한다. 원본 네 문서는 없어도 된다.

## 1. 최소 읽기

1. [PRODUCT.md](../PRODUCT.md): 제품 목적, 유지 결정, 제외 범위.
2. [MVP_PLAN.md](MVP_PLAN.md): 1~3절 전체, 지금 맡은 작업에 해당하는 계약, 9절 인수 기준.
3. UI 작업은 [DESIGN_BRIEF.md](DESIGN_BRIEF.md).
4. 버전/라이선스/원문 판단은 [SOURCE_RECORD.md](SOURCE_RECORD.md). 모든 작업에서 과거 원문을 재요약하지 않는다.

`docs/PROGRESS.md`가 생기면 먼저 읽는다. 완료된 작업을 다시 생성하지 말고 현재 코드/결과와 일치하는지만 확인한다. root package/lockfile, schema, 공통 contracts는 한 소유자만 수정한다.

## 2. 꼭 유지할 판단

- 최신 문서는 파일명 v4가 아니라 kickoff였다. ExecutionContext와 tx를 분리하고 FieldGrant read/write/export 및 BatchSaveRequest requestId/idMap 계약을 유지한다.
- Next.js + TS Worker + PostgreSQL + Drizzle + Better Auth/OIDC + AG Grid Community를 바꾸지 않는다.
- Keycloak은 제외한다. 로컬 OIDC fixture를 사용하며 실제 회사 인증/운영 NAS 검증으로 포장하지 않는다.
- 사원관리 하나로 끝까지 검증한다. Excel/PDF/Worker를 성공 JSON이나 빈 파일로 대체하지 않는다.
- Vibe HR은 작업 화면 참고, 랜딩은 타이포 참고다. 사용자가 이 방향을 확정했다. 다른 테마를 다시 제안하지 않는다.
- landing-minseok91과 vibe-hr은 사용자 소유다. 코드, 이미지, 3D 장면, 로고를 가져와 쓸 수 있다. 참조 저장소는 pull 확인을 마쳤다. 추가 변경하지 않는다.
- 실제 외부 LLM/API 키/텔레메트리/외부 폰트/CDN을 기본으로 켜지 않는다.
- S3 실제 연결, 전체 Skill, 두 번째 교육 신청 모듈은 오늘 필수 완료선 밖이다. 후속 항목을 삭제하지 않는다.

## 3. 비용을 줄이는 진행 방식

기본은 사용자에게 더 저렴한 코딩 모델 한 명이 T0~T7을 순차 수행하는 방식이다. 정확한 모델 가격과 사용자 계정의 비용은 이 계획에서 비교하지 않았다. 별도의 새 task나 유료 API 작업을 자동 생성하지 않는다.

한 번에 T 하나만 구체화한다. T0/T1/T2/T3의 공통 계약을 먼저 고정하고, T4/T5만 필요하면 독립 작업자로 나눈다. 화면 코드만 넘기지 말고 API 계약/허용 파일/해당 AC를 함께 전달한다. 검증 통과 뒤에만 다음 작업으로 간다.

실패 시 재현 명령, 오류 전문 중 관련 부분, 원인 가설 하나, 다음 확인 하나를 기록한다. 같은 실패를 두 번 반복하거나 계약 변경이 필요하면 상위 모델에 그 자료만 전달한다. 무작정 의존성 업그레이드, 테스트 삭제, ignoreBuildErrors, any 확산으로 통과시키지 않는다.

## 4. 승인과 경계

원본 kickoff는 각 Phase 승인, 인증/권한/DB migration, 새 의존성, 새 스타일, 외부 전송, 허용 목록 밖 라이선스의 사람 승인을 요구했다. 이후 사용자가 이 로컬 계획을 검토하고 코딩 진행을 지시했다. 현재 진행과 검증 범위는 PROGRESS에 남긴다.

후속 실행자가 T0에서 정확한 의존성 버전/라이선스, 초기 schema, auth 흐름을 구체적으로 정리한다. 사용자가 본 계획의 로컬 구현을 일괄 승인하면 이미 승인한 범위는 반복 질문하지 않는다. 승인 범위 밖의 외부 배포/실데이터/네트워크 전송/계약 변경은 분리한다. 커밋/push/PR은 사용자가 요청한 범위에 따른다.

## 5. 복사해서 전달할 시작 프롬프트

다음 프롬프트는 **사용자가 실제로 다음 모델에 전달할 때** 실행 지시가 된다. 지금 이 문서를 읽는 것만으로 자동 실행하지 않는다.

```text
이 저장소의 계획대로 오늘 로컬 Docker MVP를 구현해줘.
PRODUCT.md와 docs/CODING_HANDOFF.md, docs/MVP_PLAN.md를 먼저 읽고,
UI는 docs/DESIGN_BRIEF.md의 확정 방향을 따라.
원본 enterprise_ai_starter_*.md 네 파일은 삭제되어도 다시 요구하지 마.

계획에 명시된 가상 데이터 전용 로컬 MVP 범위와 디자인을 승인한다.
T0에서 정확한 의존성 버전/라이선스, 초기 DB schema와 OIDC 구성을 정리해서
내가 한 번에 검토할 수 있게 제시해줘. 승인 후 동일 범위는 반복 확인하지 마.
운영 데이터/외부 공개 배포/실제 LLM 연결은 하지 마.

T0부터 T7까지 순서대로 진행하되 전체 설계를 다시 짜지 마.
각 작업 시작 때 계획/가정/검증 기준을 짧게 밝히고,
변경 파일과 실제 검증 결과를 docs/PROGRESS.md에 기록해.
현재 코드가 있으면 이어서 작업하고 완료된 단계는 재작성하지 마.
실패 테스트를 삭제하거나 보안 검사를 끄지 마.
MVP_PLAN 9절의 P0 검사 전부가 통과해야 오늘 MVP 완료다.
P1 검증은 통과한 것처럼 표시하지 말고 후속 목록에 남겨.
S3/실 NAS/실 IdP/악성코드 검사 연계/전체 Skill/두 번째 모듈은 후속으로 남겨.
```

## 6. 작업별 짧은 전달 단위

| 작업 | 함께 읽을 계획 | 이번 작업 산출물 |
| --- | --- | --- |
| T0/T1 | MVP 2,3,8,10절 + SOURCE 버전표 | 실행 환경/호환 세트/기계적 규칙 |
| T2 | MVP 4절 + auth API | DB, OIDC 세션, 권한/감사 기반 |
| T3 | MVP 4.3,4.4,5절 | 사원 Service/API와 원자적 멱등 저장 |
| T4 | DESIGN 전체 + MVP 5절 | 실제 권한 API에 연결된 두 모드 Grid |
| T5 | MVP 6절 | 안전한 fs, 파일 상태, 업로드/다운로드 |
| T6 | MVP 7절 | queue/Worker, 실제 xlsx/pdf, 결과 재인가 |
| T7 | MVP 9~12절 | 전체 증거, README, 복구 절차, Reference Skill |

각 작업 완료 보고는 '변경 / 실제 검사 / 남은 문제 / 다음 작업' 네 항목이면 된다. 모든 검사를 매 수정마다 전부 돌리지 않고 영향 있는 검사를 먼저, 최종 조합 검사를 T7에서 수행한다.

## 7. 원본 삭제 전 확인

- PRODUCT, MVP_PLAN, DESIGN_BRIEF, SOURCE_RECORD, CODING_HANDOFF가 모두 남아 있어야 한다.
- 원본의 미래 운영/판매 요구는 PRODUCT와 SOURCE_RECORD에 보존했다.
- 원본 네 파일은 사용자가 삭제할 예정이며 계획 작성자는 삭제하지 않았다.
- `.omx`는 로컬 ignore 대상이다. 계획의 지속 보관은 root PRODUCT와 `docs/`가 담당한다. 다른 모델에게 `.omx`만 전달하지 않는다.
- 앱 구현 완료 후에는 README와 PROGRESS도 인계한다. 지금 테스트가 통과했다고 주장하지 않는다.
