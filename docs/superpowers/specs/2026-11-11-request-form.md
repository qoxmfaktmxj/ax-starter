# 공통 신청서 설계안

첫 사례는 가상 교육 과정 신청이다. 디자인 시스템의 ‘교육 신청서’에서는 과정 선택, 사유 입력, 제출 전 검토와 수정 복귀까지 체험한다. 화면을 떠나면 브라우저 초안은 끝난다. 아래의 실제 저장, 접수와 결재는 후속 설계다. 실제 과정 원장은 후속 교육 모듈이 소유한다. [제품 기준](../../../PRODUCT.md), [교육 모듈의 도입 근거](../../SOURCE_RECORD.md)

## 공통 화면과 교육 업무의 책임

| 화면 | 공통으로 제공할 구조 | 교육 업무가 결정할 내용 |
| --- | --- | --- |
| 내 신청 목록 | 신청 번호, 유형, 상태, 마지막 변경 시각, 선택 상세. 첫 신청 안내와 새로 작성 | 현재 사용자가 열 수 있는 교육 신청 |
| 작성 | 읽기 전용 신청자 정보, 업무 입력 영역, 필드 오류, 임시저장, 검토로 이동 | 과정 선택, 신청 사유, 모집 여부, 필요 서류 |
| 제출 전 검토 | 입력값을 읽기 전용으로 표시하고 수정으로 돌아가거나 제출. 기존 초안 수정은 변경 전후 비교 가능 | 선택 과정과 사유, 제출 시점 마감 여부 |
| 접수 상세 | 서버가 발급한 신청 번호, 접수 시각, 제출 내용, 내 목록으로 이동 | 접수 시점의 과정 코드와 명칭 |

첫 구현은 교육 신청 전용 타입과 Service를 둔다. 공통화할 부분은 화면 배치와 상태 전달이다. 두 번째 신청 유형이 정해지면 실제로 겹치는 코드를 추출한다.

## 상태와 저장

- 새 작성은 브라우저 초안이다. 첫 임시저장 성공 시 서버 ID와 rowVersion을 받아 ‘작성 중’이 된다. 임시저장은 필수값 일부가 비어 있어도 허용하고, 입력된 값의 형식과 길이는 검사한다.
- ‘검토’는 화면 단계다. 수정으로 돌아가면 입력과 선택이 유지된다. 제출 요청 중에는 중복 조작을 막고 성공 응답 후에만 ‘접수 완료’를 표시한다.
- 실제 교육 신청에는 결재선이 필요하다. 상신이 성공하면 신청자는 접수 번호와 결재 대기 상태를 확인한다. 승인 완료는 지정 결재자가 처리한 뒤에만 표시한다. 최초 운영 범위에서는 작성 중인 본인 신청만 수정하도록 제안한다.
- 제출 응답이 끊기면 같은 requestId로 재시도한다. 입력을 고쳐 다시 제출하면 새 requestId를 사용한다. 동일 actor/요청에 대한 중복 생성과 중복 접수를 Service에서 막는다.

## 데이터, 권한, 실패 처리

교육 신청 입력은 과정 ID와 신청 사유다. 초안 수정과 제출에는 대상 ID, 기대 rowVersion, requestId가 필요하다. 서버가 세션에서 신청자와 조직을 해석하고 DTO에 ID, 상태, 버전과 허용 필드만 담는다. 접수 번호와 시각은 서버가 결정한다.

Service는 조회/수정/제출마다 본인 행 범위와 상태, 과정의 유효성을 확인한다. 신청자 식별자와 상태를 클라이언트 입력으로 덮어쓸 수 없다. 두 탭에서 버전 충돌이 발생하면 초안을 보존하고 최신값을 다시 확인하게 한다. 성공 전이와 감사 이벤트는 같은 트랜잭션에 기록하며 감사에는 신청 사유 원문을 남기지 않는다. [사원 Service](../../../packages/server/employees/service.ts)의 멱등성 및 버전 검사 흐름을 참고한다.

첨부 허용 여부는 업무별 정책이다. 허용할 경우 초안 소유권, 파일 상태와 다운로드 시점 권한을 기존 파일 경계에서 검증한다. 목록 로딩/빈 결과/조회 실패와 권한 거부를 구분한다. 필드 오류는 입력 바로 아래에 연결하고 첫 오류로 포커스를 보낸다.

## 인수 기준

| ID | 재현 절차와 통과 조건 |
| --- | --- |
| AC1 | 신청 이력이 없는 사용자는 빈 목록에서 작성을 시작한다. 과정 찾기를 취소하면 기존 값이 유지되고 적용 시 한 과정만 입력된다. |
| AC2 | 일부만 작성해 임시저장하고 다시 열면 같은 서버 ID의 초안이 복원된다. 미저장 상태에서 이탈을 취소하면 입력이 남는다. |
| AC3 | 필수값 누락이나 마감된 과정 제출은 이유를 안내한다. 수정 후 검토 화면에 표시된 내용과 접수된 내용이 일치한다. |
| AC4 | 같은 요청을 동시에 보내거나 응답 유실 후 재시도해도 접수 번호와 성공 감사 이벤트는 하나다. 다른 내용으로 같은 requestId를 사용하면 거부한다. |
| AC5 | 다른 계정이 ID를 알아도 조회/수정/제출할 수 없다. 오래된 버전은 충돌을 표시하고 초안을 보존한다. 접수 완료 후 수정은 서버도 거부한다. |
| AC6 | 320px, 키보드와 모션 감소 환경에서 과정 선택, 오류 수정, 검토, 접수 결과 확인이 가능하다. 네 테마에서 상태는 문구로도 구분된다. |

결재 단계 수, 부서장과 교육 담당자의 순서, 책임자 공석/겸직/대결 처리, 철회 및 증빙 정책은 미확정이다. [실행 계획](../plans/2026-11-11-request-form.md)

## 참고한 업무 화면

- **신청자 화면.** SaaSFrame에 수록된 Remote 휴가 신청은 유형, 기간, 승인자에게 남길 메모와 증빙을 한 흐름에서 입력한다. 교육 신청에서는 과정과 사유를 작성하고 검토할 때 같은 순서로 읽도록 한다. [Remote 휴가 신청](https://www.saasframe.io/examples/remote-time-off-request)
- **결재자 화면.** Remote의 휴가 승인 흐름은 대기 목록, 승인, 처리 후 요약 목록을 보여준다. AX Starter의 후속 결재함도 대기 건을 열고 처리한 뒤 목록에서 결과를 확인하는 흐름으로 검토한다. [SaaSFrame 승인 흐름](https://www.saasframe.io/flows/remote-approve-time-off-request)
- **ERP 전표.** ERPNext의 입고 문서는 발주를 참조하고 품목별 인수량과 불량 수량을 기록한다. 구매 확장 시에는 승인된 요청에서 발주와 입고 문서를 추적하고, 품목별 수량은 ERP 업무에서 검증하는 구조를 참고한다. [ERPNext 입고 문서와 화면](https://docs.frappe.io/erpnext/purchase-receipt)
